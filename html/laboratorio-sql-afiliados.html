Laboratorio integrado: Oracle SQL, PL/SQL, APEX y SQL Developer/Toad

Recorrido guiado de los módulos 1 al 4 de Preparación Profesional TI – Programación. Use datos ficticios y un entorno autorizado. Cada paso se muestra de manera individual.

SQL · Paso 1 de 13

1. Comprender el requisito

Mostrar los nombres de afiliados activos y los saldos de sus cuentas. Un afiliado con dos cuentas aparecerá dos veces. Defina si el reporte debe incluir afiliados sin cuentas y quién puede consultar saldos.

Requisito RF-01: un usuario autorizado consulta exclusivamente afiliados activos y los saldos permitidos por su rol.
Comprobar comprensión

¿Qué sucede con un afiliado activo sin cuenta si usamos INNER JOIN?

No aparece; para incluirlo habría que utilizar LEFT JOIN.

SQL · Paso 2 de 13

2. Identificar tablas, relaciones y datos

El modelo de práctica usa afiliado(id_afiliado, nombre, estado) y cuenta(id_cuenta, id_afiliado, saldo). La relación se hace mediante id_afiliado.

AFILIADO: 1 | Ana | ACTIVO; 2 | Luis | INACTIVO; 3 | Marta | ACTIVO
CUENTA: 10 | 1 | 500; 11 | 1 | 200; 12 | 2 | 900
Comprobar comprensión

¿Por qué se relacionan las tablas por id_afiliado?

Porque cuenta.id_afiliado referencia al identificador del afiliado.

SQL · Paso 3 de 13

3. Construir la consulta parametrizada

Seleccione solo las columnas necesarias. El parámetro :estado permite filtrar sin concatenar entradas. El ORDER BY proporciona resultados deterministas.

SELECT a.nombre, c.saldo
FROM afiliado a
JOIN cuenta c ON c.id_afiliado = a.id_afiliado
WHERE a.estado = :estado
ORDER BY a.nombre, c.id_cuenta;
Comprobar comprensión

¿Qué valor se asigna a :estado?

ACTIVO. Se proporciona como variable bind, no concatenada al SQL.

SQL · Paso 4 de 13

4. Comprobar el resultado y las pruebas

Con los datos ficticios, Ana aparece dos veces (500 y 200); Luis se excluye por INACTIVO y Marta se excluye porque no tiene cuenta. Pruebe también varias cuentas, valores nulos permitidos y falta de autorización.

Esperado al usar :estado = ACTIVO:
Ana | 500
Ana | 200
Comprobar comprensión

¿Por qué no aparece Marta?

No tiene cuentas y la consulta usa INNER JOIN.

PL/SQL · Paso 5 de 13

5. Comprender el bloque PL/SQL

La actualización de saldo es un ejemplo distinto de la consulta de lectura. BEGIN ... END delimita un bloque ejecutable; :monto y :id son variables bind. Se deben validar el importe, los permisos y el estado de la cuenta antes de cambiar datos.

BEGIN
  UPDATE cuenta
  SET saldo = saldo + :monto
  WHERE id_cuenta = :id;
END;
Comprobar comprensión

¿Qué ocurre si :id no corresponde a una cuenta?

La sentencia actualiza cero filas; no se genera automáticamente un error.

PL/SQL · Paso 6 de 13

6. Diseñar validaciones y manejo de excepciones

Use un procedimiento controlado que rechace importes inválidos, compruebe SQL%ROWCOUNT y propague excepciones. El ejemplo es didáctico y requiere permisos y reglas de negocio reales antes de usarse.

DECLARE
  v_monto NUMBER := :monto;
BEGIN
  IF v_monto IS NULL OR v_monto <= 0 THEN
    RAISE_APPLICATION_ERROR(-20001, 'Monto inválido');
  END IF;
  UPDATE cuenta SET saldo = saldo + v_monto
  WHERE id_cuenta = :id;
  IF SQL%ROWCOUNT <> 1 THEN
    RAISE_APPLICATION_ERROR(-20002, 'Cuenta no encontrada');
  END IF;
EXCEPTION
  WHEN OTHERS THEN
    RAISE;
END;
Comprobar comprensión

¿Por qué se comprueba SQL%ROWCOUNT?

Para detectar que se haya modificado exactamente una cuenta; un UPDATE de cero filas no genera NO_DATA_FOUND.

PL/SQL · Paso 7 de 13

7. Definir transacción y trazabilidad

Una operación de aporte debe disponer de identificador de operación, control de duplicados, registro de auditoría y autorización en servidor. COMMIT y ROLLBACK deben pertenecer a una política transaccional clara; no use COMMIT automático dentro de procedimientos reutilizables.

-- En una sesión de práctica autorizada:
SAVEPOINT antes_aporte;
-- Ejecutar el bloque PL/SQL y verificar
ROLLBACK TO antes_aporte;
Comprobar comprensión

¿Por qué no se debe repetir un aporte sin control?

Porque podría incrementar el saldo dos veces; se necesita idempotencia y trazabilidad.

APEX · Paso 8 de 13

8. Diseñar la página de consulta

Cree una página APEX con un elemento de filtro P10_ESTADO y una región de reporte. La consulta del reporte usa el item como bind. Configure un esquema de autorización del lado del servidor, no solo botones ocultos.

SELECT a.nombre, c.saldo
FROM afiliado a
JOIN cuenta c ON c.id_afiliado = a.id_afiliado
WHERE a.estado = :P10_ESTADO
ORDER BY a.nombre, c.id_cuenta;
Comprobar comprensión

¿Qué hace :P10_ESTADO?

Lee el valor del item de página APEX a través de Session State como variable bind.

APEX · Paso 9 de 13

9. Proteger Session State y los saldos

Defina valores permitidos para P10_ESTADO, Session State Protection según corresponda, autorización en página y región y filtros por afiliado/usuario autorizados en el servidor. Una Dynamic Action solo mejora la interacción: no sustituye controles de seguridad.

-- Ejemplo conceptual: añadir condición de autorización
AND c.id_afiliado IN (
  SELECT p.id_afiliado FROM permiso_afiliado p
  WHERE p.usuario = :APP_USER
)
Comprobar comprensión

¿Basta con ocultar la región para impedir acceso?

No. Debe verificarse la autorización en el servidor y limitarse el conjunto de datos.

APEX · Paso 10 de 13

10. Validar interfaz y evidencias

Pruebe página autorizada, no autorizada, filtro ACTIVO, cambio de estado, sesión expirada, ausencia de registros y múltiples cuentas. Registre resultados sin publicar datos personales ni saldos reales.

Caso APEX-01: usuario autorizado + ACTIVO → muestra Ana (500 y 200).
Caso APEX-02: usuario no autorizado → acceso denegado.
Comprobar comprensión

¿Qué sucede si el usuario cambia el item desde el navegador?

El servidor debe validar el valor y la autorización antes de consultar los datos.

Herramientas · Paso 11 de 13

11. Ejecutar en SQL Developer o Toad

Conéctese solo a un esquema de pruebas autorizado. Abra SQL Worksheet/Editor, revise tablas y privilegios, ejecute la consulta SELECT con :estado y compare el resultado con el esperado. La sintaxis de definición de binds varía entre herramientas.

-- Ejemplo de SQL Developer en modo script (F5):
VARIABLE estado VARCHAR2(20);
EXEC :estado := 'ACTIVO';
SELECT a.nombre, c.saldo FROM afiliado a
JOIN cuenta c ON c.id_afiliado=a.id_afiliado
WHERE a.estado=:estado;
Comprobar comprensión

¿Se necesita COMMIT para una consulta SELECT?

No; SELECT no modifica datos.

Herramientas · Paso 12 de 13

12. Inspeccionar el plan y revertir cambios

Use EXPLAIN PLAN y DBMS_XPLAN.DISPLAY para analizar el plan estimado, no para prometer un rendimiento concreto. Si practica un UPDATE, cree SAVEPOINT y use ROLLBACK antes de cerrar la sesión; verifique que no se hayan confirmado cambios.

EXPLAIN PLAN FOR
SELECT a.nombre, c.saldo FROM afiliado a
JOIN cuenta c ON c.id_afiliado=a.id_afiliado
WHERE a.estado=:estado;
SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY);
-- Para DML de prueba: SAVEPOINT ensayo; ... ROLLBACK TO ensayo;
Comprobar comprensión

¿Qué comando deshace modificaciones pendientes?

ROLLBACK; o ROLLBACK TO ensayo si se creó un SAVEPOINT válido.

Cierre · Paso 13 de 13

13. Evaluar el laboratorio completo

Compruebe los cinco criterios: corrección funcional (SQL y PL/SQL), seguridad (bind y autorización APEX), trazabilidad (casos y auditoría), manejo de errores (excepciones controladas) y mantenibilidad (SQL legible y scripts versionados).

Evidencia: requisito → SQL → resultado → pruebas → procedimiento PL/SQL → página APEX → plan SQL Developer/Toad.
Comprobar comprensión

¿Qué evidencias deben conservarse?

Código, casos de prueba, resultados anonimizados, controles de acceso y observaciones de revisión.
