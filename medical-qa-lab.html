Medical Device / SaMD QA Lab

Simule actividades de Software Quality Engineering sobre un producto médico ficticio: ciclo de vida, requisitos, riesgos, V&V, trazabilidad, defectos y release readiness.

Alcance: todo el contenido, datos y producto son ficticios. No es un dispositivo médico real, no realiza diagnóstico ni tratamiento y no sustituye experiencia profesional en una empresa regulada. La meta es practicar artefactos y razonamiento de QA de forma demostrable.
Fundamentos

Qué está practicando

El laboratorio usa conceptos públicos y parafraseados; no reproduce el texto protegido de IEC 62304 o ISO 13485.

IEC 62304

Marco de procesos de ciclo de vida para software de medical devices. La página oficial de IEC indica que aplica cuando el software es el propio dispositivo o una parte integrada de uno, y cubre desarrollo y mantenimiento.

  • Planificación y requisitos
  • Arquitectura e implementación
  • Integración y system testing
  • Maintenance
  • Risk management
  • Configuration/problem resolution
Practicar con producto ficticio →IEC 62304 oficial ↗

ISO 13485

Sistema de gestión de calidad específico para organizaciones relacionadas con medical devices. ISO destaca requisitos regulatorios, riesgo, procesos controlados y consistencia del diseño/desarrollo y producción.

  • QMS y control documental
  • Responsabilidades y registros
  • Design & development
  • Control de cambios
  • No conformidades / CAPA
  • Evidencia auditable
Practicar con QMS ficticio →ISO 13485 oficial ↗

SaMD

FDA describe SaMD como software destinado a realizar una función de dispositivo médico sin formar parte de un dispositivo médico de hardware. El intended use es clave para determinar el carácter médico del software.

  • Intended use
  • User needs
  • Device software function
  • Riesgo y evidencia
  • Actualizaciones controladas

Caso de estudio ficticio

MedReview Trainer — SaMD Sandbox

Aplicación ficticia para que personal clínico autorizado revise registros sintéticos y marque si requieren revisión adicional. No emite diagnóstico ni recomendaciones clínicas.

Intended use de entrenamiento

Demostrar cómo documentar y probar un flujo de revisión de información médica sintética con trazabilidad y controles de calidad.

Usuarios

Revisor clínico simulado, Quality Engineer y administrador del laboratorio.

Arquitectura ficticia

Web UI → API → SQL database → audit log → report export.

Safety focus

Estado correcto del registro, control de acceso, datos completos, timestamps, auditabilidad y release configuration.

Ejemplo resueltoVV-EX · Risk Control Verification

Ejemplo de cómo llenar un artefacto

Objetivo

Verificar que un usuario Viewer no pueda abrir registros de otro equipo.

Requirement / risk

SWR-003 / RISK-SEC-01.

Ambiente

Build 1.4.2 · QA · usuario training.viewer · Team A.

Procedimiento

1) Iniciar sesión como Viewer. 2) Intentar abrir MR-10022 de Team B. 3) Revisar respuesta API.

Evidencia

La UI abrió el registro y la API respondió 200. Screenshot + network log.

Conclusión

FAIL. El control de autorización no se cumple. Bloquear release hasta corregir y ejecutar retest.
