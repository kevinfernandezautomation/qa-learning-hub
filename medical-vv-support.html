1. Intended use y usuarios

Producto: MedReview Trainer — SaMD Sandbox.

Uso previsto del ejercicio: permitir a personal clínico autorizado revisar registros sintéticos y marcar si requieren revisión adicional. No emite diagnóstico ni recomendación clínica.

Roles: Viewer/Reviewer, Quality Engineer y administrador. El acceso puede estar restringido por equipo/scope.

3. Risk Register simplificado

RISK-SEC-01

Acceso de un usuario a datos de otro equipo. Control esperado: autorización por rol/scope.

RISK-DATA-01/02

Datos incompletos o sin contexto temporal. Controles: validación de campos y timestamps.

RISK-STATE-01

La UI comunica un estado diferente al backend.

RISK-AUD-01

Acciones relevantes no quedan registradas para auditoría.

RISK-CFG-01

Evidencia asociada a una versión/build incorrecta.

RISK-PR-01

Defecto cerrado sin demostrar que la corrección fue verificada.

4. Arquitectura e interfaces

Web UI→API→SQL database→Audit log→Report export

Para Architecture / Interface Review, pregunte: ¿qué interfaz recibe el dato?, ¿qué capa aplica la regla?, ¿qué error puede propagarse?, ¿qué evidencia permite probar cada interfaz?

5. Datos para un Software System Test Protocol

Build: 1.4.2. Ambiente: QA/Sandbox. Usuario: training.viewer · Team A. Registro: MR-10022 · Owner Team B.

Formato recomendado: Objective → Preconditions → Test data → Steps → Expected result → Actual result → Evidence → Pass/Fail → Defect reference.

6. Evidencia disponible para el Validation Summary

  • Recorrido guiado de MedReview Trainer.
  • 8 respuestas del Bug Lab y sus explicaciones.
  • Traceability Matrix del laboratorio.
  • Defectos: autorización, timestamps, estado, audit log, input validation, configuration y problem resolution.
  • Build 1.4.2 y reporte inconsistente 1.4.1.
  • Decision de Release Gate y justificación.
Regla práctica: una conclusión V&V debe explicar qué se revisó, contra qué criterio, qué evidencia existe, qué desviaciones quedan y qué decisión se recomienda.
