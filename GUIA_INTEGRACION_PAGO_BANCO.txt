QA LEARNING HUB
GUÍA DE REQUISITOS Y PASOS PARA INTEGRAR PAGOS CON UN BANCO / ADQUIRENTE

Objetivo
-------
Esta guía describe una arquitectura segura y genérica para conectar QA Learning Hub con un banco, adquirente o proveedor de pagos. No contiene credenciales reales ni depende de un banco específico.

1. Requisitos previos
---------------------
1. Constituir o definir la entidad que recibirá los pagos y disponer de cuenta bancaria empresarial cuando el banco lo requiera.
2. Solicitar al banco/adquirente el servicio de comercio electrónico o pasarela de pago.
3. Completar el proceso de afiliación de comercio, KYC y contrato.
4. Solicitar ambiente Sandbox/UAT y documentación técnica.
5. Confirmar:
   - moneda(s) aceptadas;
   - Visa/Mastercard y otros métodos habilitados;
   - comisión por transacción;
   - plazo de liquidación;
   - política de devoluciones/contracargos;
   - soporte de 3-D Secure;
   - mecanismo de tokenización;
   - webhooks/callbacks;
   - llaves o credenciales separadas para Sandbox y Producción.
6. Definir la responsabilidad de IVA/facturación con asesoría contable/legal.

2. Arquitectura recomendada
---------------------------
Navegador / GitHub Pages
        |
        | HTTPS
        v
Backend seguro / API propia
        |
        | HTTPS + credenciales de servidor
        v
Banco / adquirente / gateway
        |
        +--> Webhook firmado --> Backend
        |
        +--> Confirmación --> Base de datos / orden / recibo

Nunca coloque llaves secretas del banco dentro de JavaScript público o GitHub Pages.

3. Flujo de pago recomendado
----------------------------
1. El usuario selecciona cursos y productos en el carrito.
2. El frontend envía al backend solamente IDs de productos y cantidad.
3. El backend vuelve a calcular:
   - subtotal;
   - impuestos;
   - total final.
4. El backend crea la orden con estado PENDING.
5. El backend solicita al banco/gateway una sesión, intent o payment token.
6. El usuario completa el pago en:
   a) página alojada por el proveedor; o
   b) componente/tokenización PCI del proveedor.
7. No almacenar PAN/CVV en la base de datos propia.
8. El banco/gateway procesa autenticación y autorización.
9. El backend recibe un webhook/callback firmado.
10. El backend verifica:
    - firma;
    - ID de orden;
    - monto;
    - moneda;
    - estado;
    - idempotencia.
11. Solo después de una confirmación válida se cambia la orden a PAID.
12. Se genera recibo/certificado/acceso según corresponda.

4. Requisitos de seguridad
--------------------------
- HTTPS obligatorio.
- No almacenar CVV.
- Preferir checkout alojado/tokenización para reducir exposición PCI.
- Validar PCI DSS aplicable con el adquirente.
- CSP, headers de seguridad y protección contra scripts maliciosos.
- No confiar en precios enviados por el navegador.
- Validación server-side de todos los datos.
- Rate limiting.
- Registros de auditoría sin datos sensibles.
- Secretos en variables de ambiente o secret manager.
- Rotación de credenciales.
- Verificación criptográfica de webhooks.
- Idempotency keys para evitar pagos duplicados.
- Protección CSRF donde aplique.
- Monitoreo y alertas de pagos fallidos o inconsistentes.

5. Modelo mínimo de datos
-------------------------
orders
- id
- user_id
- subtotal
- tax
- total
- currency
- status: PENDING / PAID / FAILED / REFUNDED / CANCELLED
- provider
- provider_reference
- created_at
- paid_at

order_items
- order_id
- product_id
- description_snapshot
- quantity
- unit_price
- tax_rate

payment_events
- provider_event_id UNIQUE
- order_id
- event_type
- payload_hash
- received_at
- processed_at

6. Endpoints sugeridos
----------------------
POST /api/orders
POST /api/payments/create
POST /api/payments/webhook
GET  /api/orders/:id
POST /api/orders/:id/refund

El webhook debe ser accesible desde Internet, pero debe rechazar eventos cuya firma no sea válida.

7. Pruebas antes de producción
------------------------------
- pago aprobado;
- pago rechazado;
- tarjeta expirada en Sandbox;
- autenticación 3-D Secure;
- timeout;
- doble clic en pagar;
- webhook duplicado;
- webhook fuera de orden;
- monto alterado desde DevTools;
- moneda incorrecta;
- devolución total/parcial;
- pérdida temporal de conectividad;
- reintento seguro;
- conciliación entre orden, banco y base de datos.

8. Checklist para salida a producción
-------------------------------------
[ ] Contrato del comercio aprobado.
[ ] Credenciales de Producción cargadas únicamente en backend.
[ ] Sandbox/UAT aprobado.
[ ] PCI/SAQ aplicable revisado con el banco/adquirente.
[ ] Política de privacidad y términos revisados.
[ ] Política de reembolso publicada.
[ ] Webhook validado.
[ ] Idempotencia validada.
[ ] Logs y monitoreo activos.
[ ] Conciliación probada.
[ ] Backups y recuperación probados.
[ ] Contactos de soporte del adquirente documentados.

9. GitHub Pages
---------------
GitHub Pages es apropiado para servir HTML/CSS/JS, pero NO debe conectarse directamente a una base de datos ni guardar secretos del banco.

Arquitectura correcta:
GitHub Pages -> API HTTPS propia -> Banco/Gateway + PostgreSQL

10. Referencias de seguridad
----------------------------
- PCI Security Standards Council: https://www.pcisecuritystandards.org/
- Consulte además la documentación del banco/adquirente elegido y confirme con ese proveedor qué SAQ y controles aplican a su integración.

IMPORTANTE
----------
El código visual actual de pago en QA Learning Hub es demostrativo. Para pagos reales, sustituya el formulario de tarjeta por la integración oficial del adquirente o una página de pago alojada/tokenizada.
