Caso de estudio inspirado en un flujo público de banca digital

IMPORTANTE
Este material NO automatiza la aplicación productiva de BAC, no contiene package IDs, credenciales, endpoints privados ni selectores internos. Debe ejecutarse contra una app demo, mock, sandbox o ambiente QA expresamente autorizado.

FLUJO MODELO

2. Login: usuario + contraseña.

SOLO APP DEMO / SANDBOX AUTORIZADO

Objetivo: mostrar cómo automatizar el flujo sin apuntar a la aplicación real de una entidad financiera.

Dependencias sugeridas:

- WebdriverIO + TypeScript

// pages/LoginPage.ts
export class LoginPage {
  get user() { return $('~login-user'); }
  get password() { return $('~login-password'); }
  get submit() { return $('~login-submit'); }
  get help() { return $('~login-help'); }
  get exchangeRate() { return $('~exchange-rate'); }

  async login(username: string, password: string) {
    await this.user.setValue(username);
    await this.password.setValue(password);
    await this.submit.click();
  }
}

// pages/HomePage.ts
export class HomePage {
  get accounts() { return $('~home-accounts'); }
  get transferOrPay() { return $('~nav-transfer-pay'); }
  get requests() { return $('~nav-requests'); }
  get more() { return $('~nav-more'); }
}

// pages/TransferPage.ts
export class TransferPage {
  get transferMoney() { return $('~transfer-money'); }
  get bacAccounts() { return $('~transfer-bac-accounts'); }
  get favoritesSearch() { return $('~favorites-search'); }
  get amount() { return $('~transfer-amount'); }
  get detail() { return $('~transfer-detail'); }
  get review() { return $('~transfer-review'); }
  get confirm() { return $('~transfer-confirm'); }
  get receipt() { return $('~transfer-receipt'); }

  async transferToFavorite(name: string, amount: string, detail = 'Transferencia') {
    await this.transferMoney.click();
    await this.bacAccounts.click();
    await this.favoritesSearch.setValue(name);
    await $(`~favorite-${name}`).click(); // ID de DEMO, no selector real.
    await this.amount.setValue(amount);
    await this.detail.setValue(detail);
    await this.review.click();
  }
}

// test/transfer.e2e.ts
import { LoginPage } from '../pages/LoginPage';

QA LEARNING HUB — TRANSFERENCIAS Y FAVORITOS

El Centro de Ayuda de BAC documenta que las cuentas favoritas buscan hacer transferencias más rápidas y reducir la digitación repetitiva. También indica que en Banca Móvil se puede seleccionar Transferir o pagar → Transferir dinero y elegir favoritos.

COBERTURA AUTOMATIZABLE EN SANDBOX
- Cuenta origen con/sin saldo simulado.
- Lista de favoritos vacía, pequeña y grande.
- Buscar favorito por alias/nombre.
- Ordenar recientes/frecuentes (si el producto lo implementa).
- Favorito eliminado/inactivo.
- Cuenta BAC / otro banco / SINPE según fixtures.
- Monto: vacío, cero, límites y decimales válidos.
- Descripción opcional.
- Pantalla de revisión.
- Confirmación una sola vez.
- Comprobante y retorno al inicio.
- Historial refleja operación de sandbox.

OPORTUNIDADES DE UX A VALIDAR CON USUARIOS
1. Barra de búsqueda siempre visible en favoritos.
2. Sección 'Recientes' y 'Más usados'.
3. Alias/foto/inicial del destinatario para reconocerlo rápido.
4. Acceso rápido a 3–5 destinatarios frecuentes desde Transferir.
5. Si 'Detalle' no es obligatorio, indicarlo claramente como opcional.
6. Si aporta valor, sugerencias de detalle: Alquiler, Comida, Transporte, Familia, Otro.
7. Recordar de forma local/segura conceptos recientes sin almacenar información sensible innecesaria.
8. Confirmación previa con nombre, cuenta enmascarada, monto, comisión y tiempo estimado de acreditación.

NOTA
BAC ya documenta cuentas favoritas como mecanismo de agilidad. Por ello, cualquier propuesta de 'hacer favoritos más ágiles' debe evaluarse sobre la versión concreta de la app y mediante pruebas de usabilidad, no asumirse como defecto.

QA LEARNING HUB — COMPROBANTE Y COMPARTIR

ESTADO DOCUMENTADO
BAC indica públicamente que después de una transferencia se muestra confirmación y que el comprobante puede compartirse por correo, WhatsApp u otros medios disponibles.

OPORTUNIDAD DE PRODUCTO
Reducir pasos posteriores a la transferencia sin enviar información financiera a un tercero sin consentimiento.

Alternativas a experimentar:
A. Botón principal 'Compartir comprobante'.
B. Recordar el canal preferido SOLO con consentimiento.
C. Para destinatarios favoritos, mostrar 'Compartir con [alias]' como acción sugerida, pero requerir confirmación explícita.
D. En vez de enviar automáticamente una imagen, ofrecer una notificación/confirmación dentro del ecosistema bancario cuando ambas partes sean clientes, sujeto a privacidad y reglas del producto.
E. Generar comprobante accesible en texto/PDF además de imagen.

POR QUÉ NO RECOMENDAR ENVÍO AUTOMÁTICO SIN CONFIRMACIÓN
- riesgo de enviar datos al contacto equivocado;
- privacidad;
- número de teléfono/canal puede haber cambiado;
- una transferencia no implica consentimiento para compartir información fuera del banco.

PRUEBAS
- share sheet abre una sola vez;
- cancelar compartir no repite transferencia;
- comprobante no muestra datos innecesarios;
- accesibilidad del comprobante;
- contenido correcto: referencia, fecha, monto, destinatario enmascarado;
- error al generar imagen/PDF tiene fallback;
- no se guarda el comprobante en almacenamiento público sin consentimiento.

QA LEARNING HUB — OPORTUNIDADES DE MEJORA Y MODELO DE AHORRO DE TIEMPO

DATOS DE REFERENCIA PÚBLICOS (consultados en septiembre 2026)
- Una fuente de 2025 cita al presidente ejecutivo de BAC Costa Rica indicando más de 1,7 millones de clientes.
- BAC reportó que 68,5% de su clientela era digital en 2025.
- BAC Holding reporta más de 6 millones de clientes regionales a diciembre de 2025.

IMPORTANTE: 1,7 millones NO equivale a usuarios activos mensuales de Banca Móvil. Para un business case real se necesita MAU/DAU de la app y número mensual de transferencias.

ESTIMACIÓN ILUSTRATIVA
Si se combinan 1,7 M clientes con 68,5% digital, se obtiene aproximadamente 1,164,500 clientes digitales. Es una aproximación, no una cifra oficial de usuarios activos de la app.

AHORRO PROPUESTO POR TRANSFERENCIA (HIPÓTESIS A MEDIR)
- búsqueda/selección de favorito más rápida: 10–25 s
- claridad/sugerencias en detalle: 5–15 s
- acceso directo al tipo de transferencia frecuente: 5–15 s
- compartir comprobante con acción contextual: 5–20 s
TOTAL HIPOTÉTICO: ~25–75 segundos por transferencia recurrente.

ESCENARIO CONSERVADOR PARA PRODUCT DISCOVERY
Usar 30–60 segundos como hipótesis inicial, NO como ahorro demostrado.

Si 1,164,500 clientes digitales hicieran una sola transferencia y cada uno ahorrara:
30 s → 582,250 minutos (~9,704 h) agregadas.
45 s → 873,375 minutos (~14,556 h).
60 s → 1,164,500 minutos (~19,408 h).

No debe presentarse esto como ahorro anual del banco. Para anualizar: transferencias elegibles/mes × segundos ahorrados medidos en usability testing × 12.

PLAN PARA MEDIRLO
1. Instrumentar funnel anónimo: inicio transferencia → destinatario → monto → revisión → confirmación.
2. Medir mediana y p75/p95 de tiempo por paso.
3. Separar nuevos vs recurrentes.
4. A/B test de búsqueda, recientes y acceso rápido.
5. Medir task completion, error rate, backtracking y abandono.
6. Usability test con consentimiento.
7. Ganancia = tiempo baseline - tiempo variante.
8. Solo después proyectar impacto poblacional.

OPORTUNIDADES PRIORIZADAS
- búsqueda/recientes en favoritos;
- acceso rápido a destinatarios frecuentes;
- detalle explícitamente opcional si la regla lo permite;
- fallback para imágenes;
- comprobante con compartir contextual, nunca envío externo automático sin consentimiento;
- reducir navegación redundante;
- mantener revisión final y autenticación adaptativa por seguridad.

MÉTRICAS Y OBSERVABILIDAD

Cliente/prueba:
- Throughput: operaciones completadas por unidad de tiempo.
- Response time: duración observada de la operación.
- Latency: demora asociada a la respuesta; documente exactamente qué mide la herramienta.
- Error rate: proporción de operaciones fallidas.
- Concurrency: trabajo simultáneo activo.
- P90/P95/P99: percentiles; evitan depender solo del promedio.

Aplicación:
- request rate, errores, duración, pools, colas, GC/runtime cuando aplique.
Infraestructura:
- CPU, memoria, red, almacenamiento/IO.
Datos:
- query duration, conexiones, locks, pool exhaustion, caché hit/miss.
Distribuido:
- gateway, balanceador, servicio, dependencia, DB/cache; usar correlation/trace IDs en laboratorio.

Prometheus/Grafana:
Los histogramas permiten calcular percentiles agregables. Evite promediar percentiles precomputados entre instancias. Correlacione P95/P99 con CPU/memoria/error rate y cambios de throughput.

Reporte mínimo:
Objetivo | ambiente | workload | datos | criterio | resultado | evidencia | bottleneck | impacto | recomendación | riesgo residual.

K6 + CI/CD · EJEMPLO PARA API DEMO

import http from 'k6/http';
import { check } from 'k6';

export const options = {
  stages: [
    { duration: '30s', target: 10 },
    { duration: '1m', target: 10 },
    { duration: '30s', target: 0 },
  ],
  thresholds: {
    http_req_failed: ['rate<0.01'],
    http_req_duration: ['p(90)<400', 'p(95)<600', 'p(99)<1000'],
    checks: ['rate>0.99'],
  },
};

export default function () {
  const baseUrl = __ENV.BASE_URL || 'https://test-api.example.invalid';
  const r = http.get(`${baseUrl}/health`);
  check(r, { 'status esperado': (x) => x.status === 200 });
}

NOTA
Los valores son didácticos, no SLO de BAC. En un proyecto real deben provenir de requisitos/baseline. Los thresholds convierten criterios en pass/fail y pueden integrarse en CI/CD.
